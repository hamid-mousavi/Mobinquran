# طرح فازبندی‌شدهٔ اصلاح و بهبود پروژهٔ «قرآن مبین»

> این فایل را همراه با کد پروژه (zip یا مخزن) به AI بدهید.
> AI باید فاز به فاز جلو برود و **بعد از هر فاز متوقف شود و منتظر تأیید شما بماند.**

---

## ۱. نقش و هدف

تو یک توسعه‌دهندهٔ ارشد React / TypeScript / Node و اندروید هستی. پروژه «قرآن مبین» (React 19 + Vite + Express + Dexie + PWA، استقرار روی Vercel) را در اختیار داری. هدف، اصلاح باگ‌ها، بستن حفره‌های امنیتی و هزینه‌ای، درست‌کردن اوقات شرعی و اذان، و آماده‌کردن نسخهٔ اندروید با Capacitor است. نسخهٔ وب/PWA نباید خراب شود.

## ۲. قوانین کار (اجباری)

1. فقط همان فاز جاری را انجام بده. سراغ فاز بعد نرو، حتی اگر زودتر تمام شد.
2. هر فاز روی یک شاخهٔ جدا از `main` انجام شود (مثلاً `fix/phase-1-security`) و commitهای کوچک و توصیفی داشته باشد.
3. فقط چیزهای مربوط به همان فاز را تغییر بده. اصلاح‌های اضافه و بازنویسی‌های بی‌ربط ممنوع است. اگر چیز مهم دیگری دیدی، آن را در بخش «یافته‌های اضافه» گزارش کن و اجرا نکن.
4. قبل از حذف هر فایل، فهرستش را در برنامه‌ی فاز بنویس.
5. برای هر تغییر رفتاری تست بنویس یا به‌روز کن. در پایان هر فاز این سه دستور باید بدون خطا اجرا شوند: `npm run lint`، `npm test`، `npm run build`.
6. اگر موردی مبهم است یا تصمیم محصولی لازم دارد (با علامت ⚠️ مشخص شده)، **قبل از اجرا بپرس**. بقیه‌ی موارد را با فرض معقول انجام بده و فرضت را در یک خط بنویس.
7. هیچ کلید، رمز یا توکنی را در کد یا commit قرار نده.
8. همه‌ی متن‌های رابط کاربری فارسی و RTL بمانند.
9. اگر چیزی را نتوانستی اجرا یا تأیید کنی (مثلاً تست روی گوشی واقعی)، صریح بگو که تأیید نشده؛ ادعای «کار می‌کند» نکن.

## ۳. پروتکل تأیید (Approval Gate)

هر فاز دقیقاً این چهار مرحله را دارد:

1. **برنامه:** خلاصه‌ی کوتاه چیزی که انجام می‌دهی + فهرست فایل‌هایی که تغییر یا حذف می‌شوند + سؤال‌های ⚠️ (اگر هست). **منتظر پاسخ بمان** اگر سؤال داری؛ اگر نه، ادامه بده.
2. **اجرا.**
3. **گزارش** با قالب زیر.
4. **توقف.** تا وقتی کاربر ننوشته `تأیید فاز N`، فاز بعد را شروع نکن.

قالب گزارش پایان هر فاز:

```
## گزارش فاز N
- انجام‌شده: (فهرست موارد با فایل‌های تغییرکرده)
- انجام‌نشده یا ناقص: (با دلیل)
- فرض‌ها و تصمیم‌ها:
- نتیجهٔ lint / test / build:
- تست‌های جدید:
- چیزهایی که کاربر باید دستی بررسی کند:
- یافته‌های اضافه (اجرا نشده):
- ریسک‌ها یا نکات مهم برای فاز بعد:
```

دستورهای کاربر:
- `تأیید فاز N` ← برو فاز بعد
- `اصلاح فاز N: ...` ← همان فاز را طبق توضیح اصلاح کن و دوباره گزارش بده
- `ریورت فاز N` ← تغییرات آن فاز را برگردان

## فاز ۱ — امنیت و هزینه

**هدف:** جلوگیری از سوءاستفاده از کلید AI، نشت اطلاعات و مصرف پهنای‌باند.

- [ ] **`POST /api/ai/verify-recitation`:** الان سهمیه، شناسه‌ی دستگاه و محدودیت اندازه ندارد. همان منطق `consumeDailyQuota` و اعتبارسنجی `X-Device-ID` را اعمال کن. ورودی را با zod و سقف طول مشخص (مثلاً هر متن حداکثر ۵۰۰ کاراکتر) اعتبارسنجی کن. متن کاربر باید در prompt جدا و با مرزبندی روشن قرار بگیرد تا prompt injection سخت‌تر شود.
- [ ] مقدار `process.env.VITE_GEMINI_API_KEY` را از `app.ts` حذف کن؛ هر متغیر `VITE_*` داخل بستهٔ کلاینت می‌رود. فقط `GEMINI_API_KEY` سمت سرور باشد.
- [ ] فیلد `details: err.message` را از پاسخ‌های خطا (surah، search، verify-recitation) حذف کن. فقط در لاگ سرور ثبت شود.
- [ ] **شناسایی کاربر برای سهمیه:** به‌جای اولین مقدار `x-forwarded-for` (قابل جعل) از `req.ip` با `trust proxy` درست یا هدر معتبر Vercel استفاده کن. روی Vercel مطمئن شو سهمیه با Upstash Redis کار می‌کند و به حافظه‌ی محلی (که بین instanceها مشترک نیست) تکیه ندارد. ⚠️ اگر Redis تنظیم نشده بپرس چه رفتاری می‌خواهی: رد درخواست یا فقط هشدار.
- [ ] **پروکسی صوت `/api/audio/proxy`:**
  - `fetch` را با `redirect: 'manual'` اجرا کن (یا مقصد ریدایرکت را دوباره با لیست مجاز بسنج).
  - استریم را با `pipe` و AbortController انجام بده تا با قطع شدن کلاینت، دانلود متوقف شود (backpressure).
  - فقط `Content-Type` از نوع `audio/*` پذیرفته شود.
  - rate limit ساده روی این مسیر بگذار.
- [ ] **CORS:** به‌جای `*` فقط `PUBLIC_APP_URL` و مبداهای لازم برای اپ native (`https://localhost`، `capacitor://localhost`) مجاز باشند.
- [ ] **کش‌های حافظه:** `searchCache` و `surahCache` را با سقف تعداد و TTL (LRU ساده) محدود کن. طول `q` در جستجو محدود شود.
- [ ] **هدرهای امنیتی:** `X-Content-Type-Options`، `Referrer-Policy`، `Permissions-Policy` و یک CSP حداقلی اضافه کن (در `vercel.json` یا با helmet). CSP نباید ویژگی‌های فعلی (فونت، تصاویر، Service Worker، اتصال به API) را بشکند؛ اگر لازم شد ابتدا در حالت `Report-Only` بگذار و توضیح بده.
- [ ] تست‌های سرور (مثلاً با `supertest`): اعتبارسنجی ورودی، سهمیه، رد مبدأ غیرمجاز در پروکسی، و عدم نشت `details`.

**معیار پذیرش:** هیچ endpointی که کلید AI را مصرف می‌کند بدون سهمیه نباشد؛ هیچ پاسخ خطایی پیام داخلی نشان ندهد؛ تست‌های جدید سبز باشند.
